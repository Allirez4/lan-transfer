# LAN Transfer protocol v1

This is a custom sequential chunk protocol, not tus. OpenAPI is available at `/openapi.json`; a generated snapshot is in [openapi.json](openapi.json).
All `/api/v1` routes except health and pairing require an unrevoked, unexpired session cookie or Bearer credential. The default lifetime is 30 days. All routes also enforce the configured client IP networks; health returns 503 when the database or background workers are degraded.
Cookie mutations require an exact configured Origin. Browser pairing also checks Origin.

1. `POST /jobs` with `{key, name, expected_entries?}` creates an idempotent session-owned batch. `GET /jobs/{id}` retrieves its authoritative state.
2. `POST /jobs/{id}/manifest` registers up to 500 `{key?, path, size, modified, kind, sha256?}` entries per page. Clients also bound encoded pages below 1 MiB. `kind` is `file` or `directory`; repeat source keys must match original metadata. Paths use `/`; size is an exact nonnegative integer. Chunk size is fixed at registration. `allow_conflicts: true` retains colliding entries for a decision instead of rejecting the page.
3. `POST /uploads/{id}/resolve` with `{action: "rename", path?}` or `{action: "skip"}` persists a choice before sealing. Omitting a rename path uses the suggested suffix. Entry listings expose original source keys/paths and suggested destinations; folder mappings carry through descendants and subsequent pages. `POST /jobs/{id}/seal` checks `expected_entries` from job creation or the seal body and rejects unresolved conflicts. Only sealed jobs can transfer. Folder success requires all entries completed or explicitly skipped.
4. `GET /jobs/{id}/entries?after=0&limit=500` pages queue entries by sequence. `GET /uploads/{id}` reports authoritative offset/state; `/receipts?after=0&limit=500` returns committed chunk digests with offsets >= `after`.
5. `PUT /uploads/{id}/data`: raw octet-stream with `Upload-Offset`, `Upload-Length`, `Upload-SHA256`, `Upload-Request-ID`. Exactly `min(chunk_size, size-offset)` bytes. A receipt records request ID, offset, length and SHA-256. Identical replay acknowledges without appending. Conflicting replay/offset returns 409.
6. Read/hash the selected source's committed prefix and compare every receipt before resuming. Continue one incremental whole-file SHA-256 across the suffix; retries do not hash a chunk twice.
7. `POST /uploads/{id}/complete` with `{sha256}` durably queues verification. Poll status; completion is only reported after full disk hashing and no-replace publication.
8. `POST /jobs/{id}/{pause|resume|cancel}` and `/uploads/{id}/{pause|resume|cancel}` control work. Cancellation preserves staging bytes. `DELETE /jobs/{id}/incomplete` is an idempotent, owner-only cleanup for canceled batches. It deletes unpublished staging files, preserves completed files, and records `discarded=1`.

Listings are paginated. Jobs/shares use `after=<created>&after_id=<id>` as a stable cursor, preserving records with equal timestamps. Entries/receipts use their sequence/offset cursors. Job state distinguishes registering, queued, paused, verifying, completed, failed, canceled. Individual entries additionally use uploading, finalizing, repair_required, conflict and skipped. A failed file prevents full job success but does not block healthy siblings from transferring.
Errors use HTTP 400/422 for malformed metadata, 401 for authentication, 403 for ownership/origin, 409 for state/source/path conflict, 413 for bounded request limits, 429 for rate/capacity limits, 507 for insufficient disk space. Clients stop on permanent errors and reconcile after ambiguous network errors.

`GET /shares` lists published batches and locally registered shares. `GET /shares/{id}/manifest?after=0&limit=500` enumerates paths and file IDs. `GET /files/{id}/metadata` lazily prepares a SHA-256 and pins the stat version. Content uses authenticated GET/HEAD at `/files/{id}/content`, attachment disposition, octet-stream, ETag, and byte ranges. Reliable clients send Range and If-Range, validate 206/Content-Range/ETag and verify the whole hash. They never append a 200 response to partial data. Changed registered sources return 409; register a new share to adopt changes.

Durability order: stream into one private part file → verify chunk → flush/fsync → SQLite receipt+offset transaction (`WAL`, `synchronous=FULL`) → acknowledge. Failed chunks truncate to the prior offset. Startup truncates uncommitted suffixes and marks missing committed bytes as repair_required. Finalization records expected hash and finalizing before a same-volume no-replace publication; recovery verifies an existing destination before reconciling. POSIX publication uses hard-link + unlink; Windows uses no-replace rename. Directory fsync is used where supported. Hardware/filesystem/power-loss behavior still limits guarantees.

Local administration uses the storage database, not HTTP endpoints. Revocation/expiry cancels unfinished jobs without deleting partial bytes; the owner can discard those bytes locally. Upload and download slots are separately bounded. Disconnects stop download readers, stalled writes time out, and share/device access is checked during streaming. Manifest quotas are applied atomically and do not count idempotent replays twice.
